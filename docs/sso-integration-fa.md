## ۱. مقدمه و هدف

رز هاب (Rose Hub) درگاه یکپارچه مجموعه کلینیک رز سفید است: کاربر فقط **یک‌بار** وارد می‌شود و بدون تکرار رمز عبور به سامانه‌هایی که مجوز آن‌ها را دارد منتقل می‌گردد. این سند به تیم‌های فنی سامانه‌های مقصد نشان می‌دهد چطور در کمتر از نیم‌روز، سامانه خود را به این جریان متصل کنند.

**اصل بنیادین:** رمز عبور کاربر هیچ‌گاه به هیچ سامانه‌ای منتقل یا در آن ذخیره نمی‌شود. انتقال هویت فقط با یک **توکن موقت امضاشده (JWT)** انجام می‌شود که حداکثر ۵ دقیقه اعتبار دارد.

> توجه: «داشتن حساب در رز هاب» به معنی «دسترسی به همه سامانه‌ها» نیست. مجوز ورود به هر سامانه جداگانه توسط مدیر در رز هاب تعیین می‌شود و سامانه مقصد نیز باید مجوزهای داخلی خودش را مستقل اعمال کند.

## ۲. اصطلاحات و معماری

| اصطلاح | معادل انگلیسی | توضیح |
|---|---|---|
| رز هاب | Identity Provider (IdP) | سرویس هویت مرکزی؛ کاربر را وارد می‌کند و توکن صادر می‌کند |
| سامانه مقصد | Relying Party (RP) | هر یک از ۵ سامانه مجموعه که کاربر به آن منتقل می‌شود |
| توکن SSO | SSO Token | JWT امضاشده با HS256 که هویت کاربر را به سامانه مقصد می‌رساند |
| Client ID | شناسه سامانه | مقدار عمومی که در claim `aud` توکن قرار می‌گیرد |
| Client Secret | رمز سامانه | مقدار محرمانه برای اعتبارسنجی امضای توکن؛ فقط بین مدیر رز هاب و تیم فنی آن سامانه مشترک است |

```
کاربر ──ورود──▶ رز هاب (IdP)
                  │ بررسی مجوز سامانه مقصد
                  │ صدور JWT (HS256، ۵ دقیقه)
                  ▼
   https://samane-maqsad.ir/?sso_token=<JWT>
                  │
                  ▼
        سامانه مقصد (RP)
        ۱) توکن را با Client Secret خودش اعتبارسنجی می‌کند
        ۲) کاربر را با ایمیل پیدا/می‌سازد
        ۳) نشست محلی می‌سازد — بدون فرم ورود
```

## ۳. دو سطح اتصال

| سطح | محتوا | نیازمندی از سامانه مقصد |
|---|---|---|
| **پایه (فعلی)** | ورود یکپارچه و انتقال کاربر با توکن موقت | فقط یک مسیر HTTP برای دریافت `?sso_token=` و اعتبارسنجی JWT |
| **پیشرفته (فاز بعد)** | نمایش اطلاعات و انجام عملیات از داخل رز هاب | ارائه REST API توسط سامانه مقصد + توافق فنی و مجوزها |

این سند پیاده‌سازی «اتصال پایه» را کامل پوشش می‌دهد؛ «اتصال پیشرفته» مستند جداگانه دارد (بخش ۱۵).

## ۴. پیش‌نیازهای هر سامانه

- [ ] کارکرد فقط روی **HTTPS** با گواهی معتبر (توکن روی HTTP قابل شنود است)
- [ ] وجود یک مسیر عمومی مثل `https://your-system.ir/auth/rose-hub` (یا هر مسیر دلخواه) برای دریافت توکن
- [ ] امکان نصب یک کتابخانه JWT (فهرست کتابخانه‌ها در بخش ۱۰) یا پیاده‌سازی دستی اعتبارسنجی
- [ ] جدول کاربر با فیلد ایمیل یکتا (برای تطبیق کاربر رز هاب با کاربر محلی)
- [ ] معرفی **یک نفر رابط فنی** (نام، ایمیل، تلفن) برای هماهنگی

> اگر سامانه شما فقط کلاینت-ساید است (SPA بدون بک‌اند)، اعتبارسنجی توکن در بک‌اند الزامی است؛ در این حالت با مدیر رز هاب تماس بگیرید تا معماری جایگزین (مثل BFF) بررسی شود.

## ۵. گام ۱ — دریافت مشخصات اتصال

مدیر کل رز هاب از مسیر **«مدیریت ← مدیریت سامانه‌ها»** برای هر سامانه دو مقدار صادر می‌کند:

| مقدار | مثال | محرمانه؟ |
|---|---|---|
| `Client ID` | `rose-academy-7b1d4e` | خیر (عمومی) |
| `Client Secret` | `3a7d9c1e5b8f2046...` | **بله — مثل رمز عبور** |

این دو مقدار را در فایل پیکربندی سامانه خود (`.env`) ذخیره کنید:

```env
ROSE_HUB_CLIENT_ID=rose-academy-7b1d4e
ROSE_HUB_CLIENT_SECRET=3a7d9c1e5b8f2046d0c3e7a9b1f4d628c5e0a3d7f1b9c4e6d2a8f0b3c7e5d142
ROSE_HUB_BASE_URL=https://<نشانی-رز-هاب>
```

**تمدید رمز:** اگر رمز لو رفت، مدیر کل دکمه «تمدید رمز» را در پنل می‌زند؛ رمز قبلی بلافاصله باطل و رمز جدید صادر می‌شود.

## ۶. گام ۲ — جریان ورود یکپارچه

```
┌────────┐        ۱. ورود با رمز (فقط یک‌بار)        ┌─────────┐
│ کاربر  │ ─────────────────────────────────────────▶ │ رز هاب  │
└────────┘                                            └────┬────┘
     ▲                                                     │ ۲. بررسی مجوز کاربر
     │                                                     │ ۳. صدور JWT (۵ دقیقه)
     │  ۴. ریدایرکت مرورگر                                  ▼
     └──── https://samane.ir/?sso_token=<JWT> ◀──────── سامانه مقصد
                                                             │ ۵. اعتبارسنجی توکن (سمت سرور)
                                                             │ ۶. find-or-create کاربر
                                                             │ ۷. ساخت نشست + پاک‌سازی URL
                                                             ▼
                                                    کاربر داخل سامانه است
```

نکات مهم:

- توکن فقط از طریق **پارامتر کوئری `sso_token`** به سامانه می‌رسد و **فقط یک‌بار** باید مصرف شود.
- اگر توکن منقضی شود (۵ دقیقه)، کاربر باید به رز هاب برگردد و دوباره «ورود با رز هاب» بزند؛ رز هاب اگر نشست فعال داشته باشد بلافاصله توکن جدید می‌دهد (بدون تکرار رمز).
- هر صدور توکن در گزارش فعالیت‌های رز هاب ثبت می‌شود (چه کسی، کی، به کدام سامانه، از چه IP).

## ۷. گام ۳ — اعتبارسنجی توکن

توکن یک **JWT استاندارد با الگوریتم HS256** است. چهار بررسی الزامی:

1. **امضا** — با `Client Secret` خودتان (نه راز دیگری)
2. **`iss === "rose-hub"`** — صادرکننده
3. **`aud === ROSE_HUB_CLIENT_ID`** — مخاطب فقط شما باشید
4. **`exp`** — منقضی نشده باشد (تحمل اختلاف ساعت: ۶۰ ثانیه)

فقط الگوریتم `HS256` را بپذیرید (جلوگیری از حمله algorithm confusion).

### محتوای توکن (Claims)

| Claim | مقدار | توضیح |
|---|---|---|
| `iss` | `rose-hub` | صادرکننده — ثابت |
| `aud` | Client ID سامانه شما | فقط برای شما صادر شده |
| `sub` | شناسه کاربر در رز هاب | یکتا و پایدار؛ بهترین کلید ارتباط حساب‌ها |
| `email` | ایمیل سازمانی | کلید اصلی تطبیق کاربر محلی |
| `name` | نام و نام خانوادگی | برای ساخت پروفایل اولیه |
| `role` | `SUPER_ADMIN` \| `UNIT_MANAGER` \| `THERAPIST` \| `RECEPTION` \| `INSTRUCTOR` \| `EXTERNAL` | نقش در رز هاب — راهنمای نگاشت به نقش‌های سامانه شما |
| `systemId` / `systemName` | شناسه/نام سامانه مقصد | برای ردگیری |
| `scope` | `sso-launch` | فقط ورود — هیچ مجوز دیگری |
| `iat` / `exp` | زمان صدور / انقضا | فاصله = ۵ دقیقه |
| `jti` | شناسه یکتای توکن | برای لاگ و جلوگیری از استفاده مجدد |

### همگام‌سازی ساعت سرور

برای بررسی اختلاف ساعت سرور خود با رز هاب:

```bash
curl https://<rose-hub>/api/sso/config
```

پاسخ نمونه:

```json
{
  "service": "Rose Hub SSO",
  "issuer": "rose-hub",
  "algorithm": "HS256",
  "tokenParam": "sso_token",
  "ttlSeconds": 300,
  "clockSkewToleranceSeconds": 60,
  "serverTime": "2026-10-20T06:30:00.000Z",
  "docs": "/sso-docs"
}
```

## ۸. گام ۴ — ورود خودکار کاربر

پس از اعتبارسنجی موفق:

1. کاربر را با `email` در دیتابیس خود پیدا کنید (**find**)
2. نبود؟ با `name` و `email` بسازید و نقش پیش‌فرض سامانه خودتان را بدهید (**create**)
3. اگر از قبل حساب دارد، در اولین ورود SSO، `sub` را در ستونی مثل `rose_hub_sub` ذخیره کنید تا دفعات بعد با همان تطبیق دهید
4. نشست استاندارد سامانه خودتان را باز کنید (کوکی نشست)
5. پارامتر `sso_token` را از URL پاک کنید (redirect به همان صفحه بدون پارامتر) تا در history/لاگ‌ها نماند
6. کاربر را به صفحه اصلی/داشبورد سامانه هدایت کنید

**نگاشت نقش‌ها (پیشنهادی):** نقش `role` رز هاب را به نزدیک‌ترین نقش سامانه خودتان نگاشت کنید اما مجوزهای حساس (مثل داده بالینی) را همچنان طبق قواعد خودتان صادر کنید — نقش رز هاب صرفاً راهنماست.

## ۹. گام ۵ — خروج یکپارچه

برای دکمه «خروج از همه سامانه‌ها» در سامانه خودتان:

```
GET https://<rose-hub>/api/auth/logout?redirect=/login
```

- نشست رز هاب باطل می‌شود و کاربر به مسیر نسبی داده‌شده برمی‌گردد (فقط مسیر نسبی پذیرفته می‌شود؛ ضد open-redirect).
- توصیه امنیتی: طول نشست سمت سامانه شما نیز محدود باشد (مثلاً حداکثر ۲۴ ساعت) و دکمه خروج محلی هم داشته باشید.
- خروج سراسری خودکار (back-channel logout) در فاز بعد اضافه می‌شود.

## ۱۰. نمونه کد کامل برای چهار پلتفرم

کتابخانه‌های JWT معتبر: Node.js → `jsonwebtoken` | PHP → `firebase/php-jwt` | Python → `pyjwt` | .NET → `System.IdentityModel.Tokens.Jwt` | Java → `jjwt` | Go → `golang-jwt`

### Node.js / Express

```js
const jwt = require("jsonwebtoken");

app.get("/auth/rose-hub", (req, res) => {
  const token = req.query.sso_token;
  if (!token) return res.status(400).send("توکن ارسال نشده است");

  try {
    const payload = jwt.verify(token, process.env.ROSE_HUB_CLIENT_SECRET, {
      algorithms: ["HS256"],
      issuer: "rose-hub",
      audience: process.env.ROSE_HUB_CLIENT_ID,
      clockTolerance: 60,
    });

    req.session.user = { id: payload.sub, email: payload.email, name: payload.name, role: payload.role };
    res.redirect("/dashboard"); // پارامتر sso_token با این redirect از URL پاک می‌شود
  } catch (err) {
    res.status(401).send("توکن ورود یکپارچه نامعتبر است: " + err.message);
  }
});
```

### PHP (خالص / Laravel)

```php
<?php
use Firebase\JWT\JWT;
use Firebase\JWT\Key;

$token = $_GET['sso_token'] ?? '';
if (!$token) { http_response_code(400); exit('توکن ارسال نشده است'); }

try {
    $payload = JWT::decode($token, new Key(getenv('ROSE_HUB_CLIENT_SECRET'), 'HS256'));

    if ($payload->iss !== 'rose-hub'
        || $payload->aud !== getenv('ROSE_HUB_CLIENT_ID')
        || $payload->exp < time() - 60) {
        throw new Exception('اعتبار توکن تأیید نشد');
    }

    $_SESSION['user'] = [
        'id'    => $payload->sub,
        'email' => $payload->email,
        'name'  => $payload->name,
        'role'  => $payload->role,
    ];
    header('Location: /dashboard');
} catch (Exception $e) {
    http_response_code(401);
    exit('توکن نامعتبر: ' . $e->getMessage());
}
```

### وردپرس (functions.php یا افزونه کوچک)

```php
<?php
// composer require firebase/php-jwt

add_action('init', function () {
    if (empty($_GET['sso_token'])) return;

    try {
        $payload = validate_rose_hub_token($_GET['sso_token']); // مثل نمونه PHP

        $user = get_user_by('email', $payload->email);
        if (!$user) {
            $user_id = wp_create_user($payload->email, wp_generate_password(24), $payload->email);
            wp_update_user(['ID' => $user_id, 'display_name' => $payload->name]);
            $user = get_user_by('id', $user_id);
        }
        wp_set_current_user($user->ID);
        wp_set_auth_cookie($user->ID, true);
        wp_safe_redirect(home_url('/dashboard'));
        exit;
    } catch (Exception $e) {
        wp_die('ورود یکپارچه ناموفق بود: ' . esc_html($e->getMessage()));
    }
});
```

### Python / FastAPI

```python
import os, jwt
from fastapi import Request, HTTPException
from fastapi.responses import RedirectResponse

@app.get("/auth/rose-hub")
def rose_hub_sso(request: Request):
    token = request.query_params.get("sso_token", "")
    try:
        payload = jwt.decode(
            token, os.environ["ROSE_HUB_CLIENT_SECRET"],
            algorithms=["HS256"],
            audience=os.environ["ROSE_HUB_CLIENT_ID"],
            issuer="rose-hub",
            leeway=60,
        )
        return RedirectResponse("/dashboard")
    except jwt.PyJWTError as e:
        raise HTTPException(status_code=401, detail=f"توکن نامعتبر: {e}")
```

## ۱۱. چک‌لیست امنیتی

**سمت سامانه مقصد:**

- [ ] فقط HTTPS؛ گواهی معتبر؛ HSTS فعال
- [ ] `Client Secret` فقط در env/مدیریت رازها؛ هرگز در کد یا مخزن commit نشود
- [ ] فقط `HS256` پذیرفته شود؛ `none` و الگوریتم‌های دیگر ممنوع
- [ ] بررسی امضا + `iss` + `aud` + `exp` روی هر درخواست، سمت سرور
- [ ] توکن در لاگ، URL بعدی یا HTML ذخیره نشود؛ پس از مصرف، از URL پاک شود
- [ ] اعمال مجوزهای داخلی مستقل از نقش رز هاب (به‌ویژه داده‌های بالینی/حساس)
- [ ] محدودیت نرخ روی مسیر ورود SSO (مثلاً ۱۰ درخواست در دقیقه به‌ازای هر IP)
- [ ] لاگ ورودهای SSO (زمان، ایمیل، `jti`، IP) با نگهداری حداقل ۳ ماه

**سمت رز هاب (انجام‌شده):**

- ✔ رمز عبور هرگز منتقل نمی‌شود (فقط توکن موقت)
- ✔ رمز اختصاصی برای هر سامانه + امکان تمدید فوری
- ✔ ثبت audit برای هر صدور توکن
- ✔ محدودسازی خروج یکپارچه به مسیرهای نسبی (ضد open-redirect)
- ✔ هش رمز با scrypt، محدودسازی نرخ ورود

## ۱۲. تست و تحویل

چک‌لیست پذیرش هر سامانه (قبل از تغییر وضعیت به «متصل»):

| # | سناریو | نتیجه مورد انتظار |
|---|---|---|
| ۱ | ورود با مجوز فعال | انتقال بدون فرم ورود، نشست درست |
| ۲ | ورود کاربر بدون مجوز | در رز هاب پیام «دسترسی مجاز نیست» — هیچ توکنی صادر نمی‌شود |
| ۳ | استفاده از توکن منقضی (بیش از ۵ دقیقه) | رد با پیام واضح + لینک بازگشت به رز هاب |
| ۴ | دستکاری توکن (تغییر یک کاراکتر) | رد با `invalid signature` |
| ۵ | توکن سامانه دیگر روی این سامانه | رد با `audience invalid` |
| ۶ | کاربر جدید (ایمیل ناآشنا) | ساخت خودکار حساب با نقش پیش‌فرض صحیح |
| ۷ | خروج یکپارچه | نشست رز هاب باطل؛ بازگشت به /login |
| ۸ | تست موبایل | جریان کامل روی موبایل کار کند |
| ۹ | ثبت لاگ | ورود SSO در لاگ هر دو سمت ثبت شود |

پس از تأیید همه موارد، مدیر کل وضعیت سامانه را در پنل «متصل» ثبت و تاریخ راه‌اندازی را در گزارش فعالیت‌ها می‌گذارد.

## ۱۳. عیب‌یابی

| خطا | علت و راه‌حل |
|---|---|
| `invalid signature` | `Client Secret` اشتباه است یا تمدید شده — مقدار جدید را از مدیر بگیرید |
| `jwt audience invalid` | `ROSE_HUB_CLIENT_ID` با `aud` توکن فرق دارد — مقدار را دقیق کپی کنید |
| `jwt expired` | بیش از ۵ دقیقه گذشته — کاربر را به رز هاب برگردانید |
| `jwt issuer invalid` | `iss` باید دقیقاً `rose-hub` باشد |
| `jwt malformed` | توکن کامل به مقصد نرسیده (تریم URL، پراکسی) — بررسی encode/decode پارامتر |
| کاربر منتقل نشد | مسیر `/auth/rose-hub` روی سامانه شما فعال نیست یا فیلتر احراز هویت قبلی آن را می‌بندد |
| خطای زمانی | اختلاف ساعت سرور — با `GET /api/sso/config` مقایسه کنید (تحمل ۶۰ ثانیه) |
| حلقه ریدایرکت | مطمئن شوید مسیر دریافت توکن در سامانه شما از فیلتر «لاگین اجباری» مستثنا شده است |

## ۱۴. پرسش‌نامه فنی برای هر شرکت

برای شروع پیاده‌سازی، هر شرکت این فرم را تکمیل و به مدیر رز هاب بازمی‌گرداند:

1. نام سامانه و نشانی نهایی (production) و نشانی محیط تست (staging)
2. فناوری سمت سرور (زبان/فریمورک) و امکان نصب کتابخانه JWT
3. مکانیزم نشست فعلی (کوکی سشن / JWT محلی) و طول عمر آن
4. فیلد یکتای کاربر برای تطبیق (ایمیل؟) و امکان افزودن ستون `rose_hub_sub`
5. مسیر پیشنهادی برای دریافت توکن (مثلاً `/auth/rose-hub`)
6. نقش‌های داخلی سامانه و نگاشت پیشنهادی از نقش‌های رز هاب
7. آیا سامانه API هم دارد؟ (برای اتصال پیشرفته: مستندات API، احراز هویت API، محدودیت‌ها)
8. رابط فنی: نام، ایمیل، تلفن، زمان پاسخ‌گویی مورد انتظار
9. تاریخ پیشنهادی شروع و پایان پیاده‌سازی (برنامه پیشنهادی: ۱ تا ۲ هفته برای هر سامانه)
10. نشانی دقیق `redirect` برای ثبت در پنل رز هاب (در صورت نیاز به محدودسازی)

## ۱۵. مسیر اتصال پیشرفته (فاز بعد)

پس از راه‌اندازی اتصال پایه در همه سامانه‌ها، اتصال پیشرفته به‌ازای هر سامانه جداگانه طراحی می‌شود و شامل:

- **REST API سامانه مقصد** با احراز هویت مخصوص سرویس‌به‌سرویس (service account یا mTLS)
- تعریف دقیق داده‌های قابل نمایش در رز هاب (مثلاً آمار نوبت‌ها، دوره‌ها، ارزیابی‌ها) و محدوده مجوزها — با تفکیک کامل داده بالینی از گزارش‌های مدیریتی
- ثبت توافق فنی کتبی: اندپوینت‌ها، SLA، نرخ مجاز، نسخه‌بندی API، مالکیت داده و مسئولیت پشتیبانی
- اضافه‌شدن «اتصال پیشرفته» به قرارداد پشتیبانی هر سامانه

---

**تماس:** برای دریافت مشخصات اتصال یا هماهنگی، با مدیر کل رز هاب (مسیر «مدیریت ← مدیریت سامانه‌ها») در ارتباط باشید. نسخه رسمی این سند در مخزن کد رز هاب (`docs/sso-integration-fa.md`) نگهداری می‌شود و نسخه Word آن از مدیر پروژه قابل دریافت است.
